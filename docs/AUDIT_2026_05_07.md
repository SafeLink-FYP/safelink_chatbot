### 1.2 Knowledge-base entry shape (one representative entry, copy-pasted)

`data/knowledge_base.json` is a flat JSON **array** (not an object with an `entries` key). Each element:

```json
{
  "id": "earthquake_during_1",
  "disaster_type": "earthquake",
  "category": "during",
  "title": "Earthquake Safety — During the Shaking",
  "content": "**DROP, COVER, and HOLD ON!**\n\n1. **DROP** to your hands and knees immediately\n2. **COVER** your head and neck under a sturdy desk or table\n3. **HOLD ON** until the shaking stops\n\n**If Indoors:**\n- Stay inside — don't run outside during shaking; falling debris in narrow lanes is the biggest killer\n…",
  "searchable_text": "earthquake what to do during earthquake safety drop cover hold shaking tremor seismic indoors outdoors vehicle",
  "source": "NDMA Pakistan; USGS public guidance",
  "metadata": { "verified": true, "last_updated": "2026-04" }
}
```

Top-level fields per entry:
- `id` *(string, snake_case_with_index)*
- `disaster_type` *(enum: `earthquake | flood | heatwave | cyclone | fire | gas_leak | building_collapse | general`)*
- `category` *(enum: `during | before | after | first_aid | general`)*
- `title` *(string)*
- `content` *(markdown string)*
- `searchable_text` *(string — used for TF-IDF index in addition to title+content)*
- `source` *(string — semicolon-separated sources, no URLs)*
- `metadata` *(object, observed keys: `verified`, `last_updated`, `disclaimer`)*

> **Master-prompt deviation #3:** §8.1 specifies a richer schema with `phase`, `audience`, `locations`, `sources` (list of `{name, url}`), `last_verified`, `priority`, etc. The current schema does **not** match. Migration in Phase 2 is **additive + reshape** — see Phase 0.5 plan. Notable mappings:
> - current `category` ≈ master-prompt `phase`, but the value space differs (current `first_aid` is treated as a phase, not a separate facet).
> - current `source` is a single semicolon-separated string with no URLs; target is a list of `{name, url}` objects.
> - `searchable_text` has no equivalent in the target spec but is currently used by `KnowledgeRetriever._searchable()`. Keep it (or fold into `tags`/`summary`).
> - `metadata.disclaimer == "first_aid"` is the current marker that triggers `FIRST_AID_DISCLAIMER` — rename/repurpose to a top-level `disclaimer` flag in the new schema.

## 3. Frontend conventions

### 3.1 `AppSecrets` pattern (`lib/core/secrets/app_secrets.dart`)

- All values are **`static const String`** literals committed to the repo.
- One exception: `mlApiBaseUrl` is a **getter** that branches on `Platform.isAndroid` to return `http://10.0.2.2:8000` vs `http://localhost:8000`.
- There is **no `--dart-define` reading** anywhere in the file; build-time configuration is not used today.
- `googleWebClientId` exposes a "configured?" helper (`isGoogleSignInConfigured`).
- The Supabase URL and anon key are real production values (not placeholders).

> **Master-prompt deviation #4:** §7.2 F1 says to read `CHATBOT_BASE_URL` via `--dart-define` "with sane defaults per platform." The repo does **not** use `--dart-define` today. Phase 1 should follow the existing `mlApiBaseUrl` getter pattern (platform-aware getter) for `chatbotBaseUrl` and *additionally* allow override via `String.fromEnvironment`. Don't introduce a brand-new pattern that diverges from `mlApiBaseUrl`.

### 3.2 `InitialBindings` pattern (`lib/core/di/initial_bindings.dart`)

- All registrations are eager `Get.put<T>(..., permanent: true)` — **never `lazyPut`**.
- Order matters and is documented (`MlAlertController` after `MlAlertService`, `AlertController` after `MlAlertController`).
- `ConnectivityService`, `OutboxService`, `OutboxController` are registered **earlier** in `main.dart` (before `runApp`) because Hive boxes must be opened first.
- `ChatbotRepository` and `ChatbotService` are already registered as permanent singletons in `InitialBindings:42–46`. **`ChatController` is NOT in `InitialBindings`** — it is `Get.put`-ed in `_ChatViewState`'s field initialiser (audit F7).

### 3.3 `OutboxService` interface (paste)

`features/outbox/services/outbox_service.dart`:

```dart
class OutboxService extends GetxService {
```

Payload shape (`PendingSubmission`): `{id, kind, payload (Map<String,dynamic>), createdAt, attempts, lastError}`. Persisted as `Box<Map>` — no `TypeAdapter`. Discriminator is `SubmissionKind.{sos, disasterReport}`.

> **Master-prompt deviation #5:** §5.1 says to read `core/services/connectivity_service.dart` and `core/services/outbox_service.dart`. They actually live under `features/outbox/services/`. The chatbot feedback outbox should also live under a chatbot path (e.g. `features/chatbot/services/feedback_outbox_service.dart`) and **mirror this exact public API shape** — including a chatbot-specific `SubmissionKind.chatbotFeedback`.

## 7. Deviations from master prompt

Numbered for cross-reference in Phase 0.5 plan and PR descriptions.

1. **`ChatRequest` already has `province` and `city`.** No backend schema migration needed for Phase 1 wiring; the Flutter side just needs to start sending them.
2. **`ChatResponse` field names diverge from §9.6 sketch** (current: `response`, `urgency_level`, `intent: IntentResult`, no `sources`/`used_llm`). Phase 3 must extend additively, not rename.
3. **KB schema diverges materially from §8.1 target** (flat array vs `{version, updated_at, entries[]}`; `category` vs `phase`; single-string `source` vs `[{name, url}]`). Phase 2 needs a real migration, not a relabel.
4. **`AppSecrets` doesn't use `--dart-define`.** Match the existing platform-aware getter pattern (`mlApiBaseUrl`) for `chatbotBaseUrl`, optionally with `String.fromEnvironment` override.
5. **`ConnectivityService` and `OutboxService` live under `features/outbox/services/`, not `core/services/`.** Mirror the location convention by putting the chatbot feedback outbox under `features/chatbot/services/`.
6. **`ProfileModel.province` is missing** (only `region` and `city` exist). Adding it touches the Supabase `profiles` table — out-of-scope per master prompt §4 ("don't touch authorization, profile features"), so derivation from `city` may be the only acceptable path. Decision needed.
7. **Chatbot backend is not deployed.** Phase 1 must include creating a Railway (or equivalent) deployment. Human action required to capture the URL and set secrets.
8. **`CORS_ORIGINS` env var is named `CORS_ORIGINS`, not `CORS_ALLOWED_ORIGINS`.** Aliasing in Phase 1 keeps `.env.example` stable; renaming risks breaking anyone's local `.env`. Recommend keep `CORS_ORIGINS` and just document.
9. **`.env.example` documents `RETRIEVAL_SCORE_THRESHOLD=0.25` while `config.py` defaults to `0.15`.** Sync the two in Phase 1.
10. **README.md is stale** — references `chatbot_server/` (the directory was renamed to `chatbot_backend/`), claims "Earthquake and Flood" coverage only, and instructs editing `chatbot_service.dart` directly (file no longer exists at that path). Should be rewritten in Phase 5.
11. **`uuid` is a transitive dependency, not direct.** Phase 1 F13 needs to add it as a direct dependency in `pubspec.yaml`.
12. **`slowapi`, `google-generativeai`, `groq`, `httpx[brotli]` are not in `requirements.txt`.** Phase 1 (slowapi) and Phase 3 (LLM SDKs) add them.
13. **KB has 27 entries, not "~28" as the prior audit said.** Trivial difference; flagged for accuracy.
14. **`category` value `first_aid` is conflated as a phase.** First-aid entries have `disaster_type: "general"` and `category: "first_aid"` — that's an orthogonal facet, not a phase. New schema should split `phase` and `topic`/`audience` cleanly.
15. **Mental health KB is one entry** (`mental_health_post_disaster_1`, `disaster_type: "general"`, `category: "first_aid"`) — Phase 2 needs to expand this to a full `disaster_types: ["mental_health"]` cluster.
16. **`OfflineDataResponse` at backend has more fields than the Flutter model reads.** Backend produces `version`, `last_updated`, `guidance_data`, `helplines`, `quick_tips`, `emergency_keywords`, `checksum`. Flutter `OfflineData.fromJson` reads helplines, quick_tips, emergency_keywords, last_updated only. Phase 4 F8 fixes the consumer; backend untouched.
17. **`scripts/` directory does not exist.** Phase 2 §8.6 (`scripts/validate_kb.py`) creates it.
18. **No `Makefile` exists.** Phase 2 §8.6 (`make validate-kb`) introduces one. Decide in 0.5 whether a Makefile or a Python script entry-point is preferable on Windows-first dev environments.
19. **`tests/` directory does not exist** in `chatbot_backend/`. `pytest`/`pytest-asyncio` are in `requirements.txt` but no test file exists today.
20. **No `prompts/` directory exists.** Phase 3 (`prompts/system_prompt.txt`) creates it.
